# 体系语言与协议表示

> 本文保留研究设计与初始语法草案。首个可执行v1已经实现，实际字段、算子语义、状态机及命令以 [体系语言v1与执行器](07-executable-systems.md) 为准。初始示例不应直接当成当前解析器输入。

> v2在保持v1兼容的基础上增加通用公开上下文、参数状态、声明标签和动态动作，见 [通用协议v2](08-general-protocols-v2.md)。它不把私有trace作为协议状态，也不自动推断未定义的好套或赢墩。

## 1. 定义原则

结构化并不意味着只允许简单特征。初版语言应能组合概念、上下文和多轮协议，以便之后扩展到控制扣叫、关键张、接力及全新的信息编码方式。

自然语言和可执行程序来自同一份 IR。解释性文字可以补充动机，但不能暗中改变可执行语义。无法生成完整说明的可执行扩展，不作为正式候选发布。

初版实现一组足够打通实验的算子，不要求立刻实现所有桥牌约定。每个缺失能力标记为实现限制，不能宣称该能力被研究目标排除。

## 2. 顶层结构

建议字段：

```text
schema_version
system_id / content_hash / parent_hashes
name / changelog
feature_definitions
protocol_definitions
decision_rules
fallback
required_operator_versions
```

JSON 为权威定义；自然语言说明通过确定性渲染器生成。导出的说明列明 schema、特征和算子版本。将 JSON 往返保存后，执行语义和内容哈希应保持不变。

## 3. 特征和表达式

| 类别 | 需要逐步支持的能力 |
| --- | --- |
| 基本手牌 | HCP、套长、具体牌张、均型、缺门和单张 |
| 套质量 | 指定大牌是否齐备、前 N 张中的数量、明确公式定义的质量分 |
| 控制 | 某花色首轮/次轮控制；是否计短套必须由当前约定明确 |
| 组合 | 指定大牌组合、跨花色条件、与已确定将牌的关系 |
| 上下文 | 角色、局况、Pass 身份、叫牌序列、已同意将牌、协议阶段 |
| 组合算子 | and/or/not、比较、算术、集合成员、存在/全称等受限组合 |

每个新概念必须有精确语义。例如“好六张套”不能成为未经定义的原语；应展开为具体牌张条件或确定公式。允许体系自己定义这种公式，不强制采用人类常用标准。

派生特征可以复用其他特征，要求类型检查、无循环依赖，并展开进自然语言说明。初版不支持任意 Python `eval`、动态导入或访问外部状态。

## 4. 决策规则草案

以下片段仅展示候选 IR 语法，最终 schema 由实现者固定并为所有示例补充测试：

```json
{
  "id": "open_1nt",
  "priority": 100,
  "when": {
    "all": [
      {"feature": "auction.has_contract_bid", "op": "eq", "value": false},
      {"feature": "hand.hcp", "op": "between_inclusive", "value": [15, 17]},
      {"feature": "hand.shape_sorted", "op": "in", "value": [[4, 3, 3, 3], [4, 4, 3, 2], [5, 3, 3, 2]]}
    ]
  },
  "action": {"call": "1NT"},
  "meaning_ref": "opening_1nt_natural"
}
```

语义约定：`auction.has_contract_bid` 只检查定约叫品，不把 Pass 视作定约叫品；此示例允许在无人开叫时、任何轮到自己的位置按相同条件开叫。

规则按 priority 降序选择；同一最高优先级多规则同时命中视作冲突，不依赖 JSON 顺序偷偷决定。候选校验尽量提前发现冲突，运行中遇到冲突则使该次候选评测无效。

兜底可以明确规定 Pass。高优先级命中规则若输出非法叫品，不能悄悄降到低优先级或改成 Pass。若希望“仅在某动作合法时适用”，必须在条件中显式使用 `is_legal`，并在说明中写出。

## 5. 含义与决策分开

`decision_rules` 决定实际怎么叫；公开含义描述这一历史下该叫品的约定及可推断范围。含义可以宽泛，不能错误排除协议实际允许的情况。

根据一条规则给出含义时，需要考虑更高优先级规则已排除的情况；同一叫品可能来自多个分支，其完整含义可能是多个条件的并集。不能只渲染最后命中的一句话并称其为完整体系。

完整自然语言说明必须包含决策顺序、所有规则和兜底，因此即使短版约定摘要不精确，完整规范仍应能够重建策略。正式发布时还要检查摘要没有自相矛盾。

## 6. 多轮协议

协议最少定义：进入条件、参与角色、状态、各阶段可发出的信息、公开状态转移、退出条件和异常路径。初版可由完整历史每次重建状态，避免跨牌污染。

协议状态示例：

```text
已确定将牌
→ 发起关键张询问
→ 按本体系规定的映射回答
→ 询问将牌 Q（可选）
→ 询问边花控制/边花 K（可选）
→ 停叫或选择最终定约
```

这个示例不是完整 RKCB 规范。任何实际实现都必须明确：将牌怎样确定、哪张 K 算关键张、回答映射、哪些回答有歧义、如何区分、问将牌 Q 的叫品、回答顺序、对手干扰和叫牌空间不足时的处理。不能直接写“按标准 RKCB”。

新约定不要求沿用传统名称或含义。含义变更必须一并更新发送规则、解释规则、状态转移、后续回答与说明。移除一段协议也必须修复所有引用。

## 7. 变异类型

1. 参数变异：调整范围、阈值、特征权重或回答区间。
2. 条件变异：加入套质量、控制、特定牌张组合等条件。
3. 划分变异：拆分/合并手牌类别和回答分支。
4. 语义变异：重新分配叫品含义，同时修改相关搭档规则。
5. 协议变异：插入问叫、改变信息传递顺序、改变退出路径。
6. 结构变异：重组开叫或整段子体系。

初期一次只改一个明确假设，便于归因；后期可提出较大修改。不得因为候选说明长或结构陌生而拒绝。

若提案需要新算子，应进入语言扩展队列：实现精确语义、渲染和测试后重试，而不是把临时代码注入当前候选执行器。

E003已开放**整个现有v2定义**的研究编辑：规则、优先级、特征、公告、状态/转移、回答和fallback均可增删重写，允许一次替换完整体系。旧版提案器的8处编辑和规则ID白名单不是语言限制。工作版本可以暂时不合法，但冻结发布必须编译、生成完整说明、通过可执行测试，并至少有一个相对父版本真正改变叫牌的测试见证。详见[E003](12-self-evolution.md#17-e003自主研究agent)。

## 8. 校验层次

- 语法/类型：schema、字段、引用、返回值、表达式类型、特征依赖无环。
- 协议完整性：每个分支有后续或退出；角色和公开状态转移明确。
- 决策完整性：优先级、重叠规则和兜底明确；新规则与既有规则共同校验。
- 场景检查：所有修改分支至少有命中、边界和相邻分支样例。
- 运行检查：随机合法牌例中无非法输出、冲突、崩溃或跨牌残留。
- 说明检查：所有可执行节点均有说明；抽样逐步解释可与实际 trace 对照。

随机测试不能证明所有情况都正确；校验报告应明确静态证明、有限枚举和抽样检查各自覆盖了什么。
