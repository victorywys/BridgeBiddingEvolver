# 负责人驱动研究与独立维护

## 研究闭环

控制台默认采用`research_architecture="director"`、`research_budget_mode="campaign"`。手工旧配置未声明时仍为`legacy`／`episode`，历史运行与分数不覆盖。新示例：[E015](../experiments/e015-expanded-directed-research.json)；它依赖本机E014r1的冻结亲本与研究工作区，克隆仓库不携带运行数据。[E014](../experiments/e014-directed-research.json)保留为旧额度对照。

[E017](../experiments/e017-coverage-first-research.json)承接本机修复后的冠军、基线、保留草稿和发布物，采用覆盖优先草拟：先保存完整阶段表并成片补齐关联内容，允许未测试工作版；随后批量验证、修复反例并发布，不要求每增加一条规则就先运行测试。其新授权为研究600M token／10000请求、独立维护200M token／4000请求，最多72小时，单项4000回合／12小时；原账与成绩不重置。48个研究单元每项最多2个假设仍由单协调器顺序执行，不是96个并行agent。该配置依赖本机冻结运行，克隆仓库不携带它们。覆盖表是工程进展，不取代真实比赛fitness，未测试草稿也不是已验证体系。

```text
研究负责人：体系语义、诊断、历史结论，需要时查证
  → 结构化假设：机制 / 接口 / 实现目标 / 怎样证伪
  → 独立执行者：可行性、IR实现、自然牌例、边界/干扰回归
  → 程序试验：定向环境、自动扩样、真实DDS与变化覆盖
  → 可信队列：冻结、真实回归、另一批共同新牌、挑战届时的冠军
  → 执行报告：实际结果 / 弃权贡献 / 局限
  → 负责人：继续、证伪、结构重设计、融合保留方案
```

负责人可以按需查询同源体系说明、工作进度、保留分支、候选与挑战队列，但没有编辑体系、对手或评分权限。执行者不能决定实验裁决。新颖性、复杂度与规则数量不进入适应度。

当前为单协调器顺序调度隔离任务，`workers`只控制比赛并发；不是分布式多执行者并行。发布后立即进行可信评价并回报，不让执行者为了等待尚未调度的结果反复读取。

## 全局管理者：硬交接与可检验交付

新实验可显式启用；省略时保留旧调度，不给历史实验补写管理记录：

```json
"campaign_manager": {"turns": 24, "seconds": 900, "max_missed_deliveries": 2, "solution_return": true}
```

此配置要求`director`＋`campaign`。全局管理者统筹全部工作区、保留分支、候选、维修与评价队列、未完成项及剩余额度；原负责人仍负责体系假设，实现者修改IR，维护者交付修订，宿主独立评价。全局管理请求单列角色费用，使用既有研究池；接口纠错仍按原规则计维护。

### 强制周期返回方案

`solution_return=true`时，研究实现者、基线维修实现者和隔离工程实现者均按有界函数调用工作：**本周期必须返回基于当前研究的具体最佳方案，可以不完善，但不能仅报告进度、阻塞或“还要继续研究”。** 默认推荐24轮／900秒，而不是6轮／180秒。

- 每次实际发出的对话都附带剩余秒数、剩余轮次、绝对截止时间和交付要求；咨询也占本周期请求槽位，不能挤掉最后的返回槽位。倒计时单独附在本次请求中，不把一串过期倒计时加入后续对话。
- 最后一轮，或进入预留收口时间（最多120秒、短周期取四分之一）时，只提供`return_solution`，并通过Responses API的`tool_choice`强制该函数；不再允许查资料、编辑或咨询。提前结束、仅返回文字、工程阻塞或研究操作数耗尽，也必须先给方案。
- 返回物包含具体选择、公开依据、已知局限和下一步。宿主附带真正保存的IR／代码／测试证据，而非采信模型自称“测试通过”。未实现、未编译、未测试的方案允许交付，但不能因此发布候选、接受维修或宣称晋升。
- 截止时钟和已用请求数落盘；恢复不延长本周期，不重复调用模型。已付费且已保存的返回响应允许在恢复后落盘，同时明确记录晚于截止的秒数，不冒称准时。
- 网络请求按实际剩余时间设置超时；工程测试子进程沿用同一剩余时间，支持停止回调的工具在收口边界让出。被中断的工具保留已有工作并明确标为未完成，不伪造成功。管理／独立复核是另一次调用，不占用已经返回的执行周期。
- 为方案返回预留请求和token；小余额不足以同时研究并收口时，直接用现有证据返回方案，不先花一次完整管理调用后零交付。研究与维护仍只用各自真实余额，不互借、不重新授权。
- 工程周期方案不是正式修订提交：返回后保留工作稿、增加周期编号再继续，原反例复放、回归、原引擎复现和独立审查门禁保持不变。

真正的网络／基础设施故障仍可能导致没有合法模型方案：此时明确记录`failed`／`delivery_failed`、保留原始响应、当前工作与先前方案，不用宿主捏造一份“成功交付”。控制台分别展示方案、局限、倒计时历史和实际证据，下载内容按不可变hash校验。

为兼容旧冻结配置，省略`solution_return`或设为`false`仍采用旧的安全边界接管：只在完整模型／工具结果保存后交还管理者，单次长调用不被截止点中断。**这种旧模式只能保留工作和责任，不等于上述强制方案交付。**

合同仍指定下一研究目标及证据类型：带阶段表的改动草稿、当前稿新增通过回归、实际机制试验、真实失败反例，或通过原门禁发布的候选。**开启强制返回时，本周期有具体方案即履行方案返回义务，不等于这些研究目标已实现。** 宿主按真实工具结果和版本身份验收研究证据，不采信“已完成”自述、规则数或已过期测试；相同稿反复重跑原已通过测试不算新增证据。未测试快照明确是未发布草稿，不登记为比赛体系。可编译草稿连续两次纯草拟后必须转入验证／实验／反例／发布；不能编译的候选先恢复编译，不安排注定无法运行的验证。一次未达标不能原样续期，达到配置中的连续次数后只允许暂停／结束执行者，可同时派出更小的补缺任务。任务主动收尾也需要全局管理复核。

补缺任务是持久全局队列，不只写在提示词里：包含完整假设、所属谱系、优先级及可选`continue_from`／`base_candidate`，下一个对应谱系的研究单元优先实际领取，复用隔离工作区和原预算。领取、决策、工作指令均幂等；重启不重复派单或模型收费。新引擎续接会映射未完成任务的保存分支，保留缺口清单，不将旧验收或成绩冒充新run结果。

管理者通过结构化`task_updates`真正暂停、取消、改优先级或恢复待办，不能仅在文字中声称“旧任务后置”。更新必须指向待领取／暂停任务并说明原因；已经领取的执行仍走交付决策。恢复暂停工作使用其实际保存会话而非过期输入，暂停状态跨续接保留，最后调度理由随任务可查。

管理者自身每次检查也受6次模型请求／120秒约束；已有响应可恢复处理，不再发超期请求。未能及时给出合法决策时，宿主明确记录管理失败并暂停分支，界面区分宿主暂停与模型交付，不编造验收。管理上下文提供冻结配置的实际限额、已用及剩余额度；旧任务文字中的600M等历史分配不能成为新授权。

多轮续接中，新一轮`g001`不得覆盖已有`imported-g001`：冲突分支增加完整来源run命名空间，同时保存旧ID到新ID的映射，管理队列按映射继续真实工作区。编译无效但已保存的候选IR仍可查证：协议查询返回文档身份、编译错误及阶段设计，而非把真实草稿缺陷误算成查询格式错误并不断重试；原始IR的修复属于实现者，只有真实基线／引擎故障才交独立维护。

新派单ID也包含完整run命名空间，不能因本轮再次从`r0001`编号而被继承的旧任务遮蔽。续接旧格式时，若原始已落盘决策中的派单被同ID历史任务占位，则从该真实决策恢复未派出的任务并记录来源；不重发已完成任务，也不新增模型调用或改写旧账。

控制台展示当前合同、截止时间、连续未交付次数、宿主验收、管理决策、补缺派单和不可变阶段快照下载。快照含IR、阶段设计、作者测试及其所用牌、最近实际结果；其hash随原实验保存，后续编辑不能把旧快照变成新稿。完整诊断牌库仍在原工作区，不为每次交接重复复制所有牌和操作历史。

## 约定以完整叫牌阶段为设计单元

不是先发明一个孤立叫品再补搭档反应，而是：

```text
公开可达进程／双方已知信息
  → 本阶段行动者的手牌分区
  → 每个相关叫品的发送条件／真正公开承诺
  → 同伴接续、干扰后的责任与停止／退出条件
```

负责人在已有`mechanism`／`implementation`中给出阶段结构、编码想法与证伪要求，不亲自逐节点查IR；执行者细化分区、优先级及实现，报告遗漏、重叠、遮蔽、歧义和无法履约的逼叫责任。发送条件不是公开保证：两者必须分别实现和审查。改一叫要同步接收含义、后续与退出，用空前缀自然见证和定向边界／干扰案例验证，不能仅凭注入进程证明可达。

`update_implementation_state`增加可选`stage_design`，保存可读的“公开进程—手牌分区—各叫品—接续”表，随工作区／交接保留；原有阶段、事实、阻碍与下一步不变。复用这份设计，只补查变化／缺失接口，不每次重新理解完整体系。人类可从[进程审查页](13-system-navigation.md)查看冻结版本、固定草稿及同进程亲本对照。文字长度、风格、新颖性与复杂度仍不进入fitness，未完成设计可保留但不能冒充已验证。

本指导属于新引擎身份，只作用于之后使用它的新实验；进行中的实验继续使用其冻结代码与prompt，不能热改旧记录或引擎hash。

## 显式的大额度，而不是隐藏的小上限

| 配置 | E015 | 含义 |
|---|---:|---|
| 研究单元／每单元假设 | 12／4 | 可少提、停掉无效方向，不以任务数作为成绩 |
| 研究请求／token | 3600／120M | 正常设计、查证、讨论共用研究池 |
| 单项回合／时间护栏 | 1600／4小时 | 每项完整可用，不按假设数均分 |
| 输入字节／输出token | 2MB／65536 | 输出包含推理；均为上限，不是目标用量 |
| 案例／DDS探索 | 各100000副／任务 | 独立额度，不再争抢256副 |
| 比赛配对／研究活动时间 | 600万／40小时 | 程序发牌不逐副用token，但仍消耗CPU、DDS和时间 |
| 独立维护请求／token／时间 | 1000／20M／6小时 | 不占研究池；原失败和真实总费用保留 |
| 自动修复／候选挑战次数 | 100／200 | 不再由一个工单或同代占位锁住 |

研究发牌显式使用更大的内部额度；公共审计仍限每批1000副、最多100万次发牌尝试，不随研究案例额度放宽。

`episode`保留旧语义：单元内各任务共享并均分回合／时间；没有独立维护配置时费用共享。`campaign`使用全局研究预算，单项护栏不因拆任务而缩小；不等于无限资源。恢复不重置任何账本。

正式开发评价使用64／256／1024副，挑战使用另一批2048副共同均匀牌；`parent-improvement`以相对实际冠军均值大于零进行开发接受，不冒称统计确认。另有同批历代成长复核。条件试验成绩不能拿来声称总体变强。

## 不再反复从导航起点理解体系

campaign启动时预加载可容纳的真实当前IR工作集，最多512节点，工作集最多768KB或输入护栏的一半；依赖未加载、节点失效／变化均明确标记。编辑后从当前源更新，不把旧内容伪装成新版本。

自动压缩阈值为实际请求体护栏的92%，不再沿用250KB输入的70%阈值。工作集、阶段、阻碍、下一步、协议目标、管理交付合同和真实评价随压缩交接；完整工具证据仍保存在工作区。未启用全局管理时，连续无信息读取会提示，但campaign不因第12次读取强行结束任务；启用后交还管理者调整，而非丢弃草稿。旧episode保留原门槛。

普通上下文重建、自动交接、低余额聚焦及方案收口使用同一原子证据装配器。最新工具调用和返回成对保留，不交给递归摘要器；当前任务合同保真，旧节点／原始分页按完整单元装入，不能把执行条件压成字段数量后仍声称模型已经读过。重复的最新原文不再同时塞入工作集和工具返回。放不下的旧证据明确列为未装入；即使最新结果超过整个输入上限，也只能给出明确“未送达”的收据和可补读引用，不能伪装成完整结果。

研究进度笔记不是不可裁减的任务合同：`implementation_state`作为独立完整单元排在最新原文之后，不再同时嵌入工作集。空间不足时整项明确标记未送达并保留工作区指针，不能让数KB旧设计笔记把刚读取的当前源代码挤出预算；空间充足时原样保留笔记。

原始读取按规范化参数、节点内容版本及实际分页字段范围复用；节点内容改变或字段重排导致分页范围变化后，缓存及工作集中的旧页均失效，避免只比较无序内容哈希而重复／漏读字段。同版本再次索取允许返回真实缓存，不因“曾存盘”就禁止模型补读。分页提供`next_offset`，原始页面记忆的容量与实际工具返回上限一致，不再静默漏记超过12KB但合法返回的页面。

研究请求和工具式管理／维修请求均保存实际输入、工具集合、请求体字节哈希及工具结果清单。研究账本区分`prepared`与网关已返回的`received`；只有后者登记已送达的具体工具结果哈希。存档、缓存命中与当前请求送达不是同一状态。预算聚焦按实际剩余输入空间装配，倒计时也计入请求预估；不增加授权、不借维护池。

截止时发送的延期消息可以对应尚无`result`的`started`操作：消息已收到不等于工具已完成。只有操作为`completed`、实际存在结果且哈希匹配时才记录完整送达；同一调用后续真正完成时可更新回执，不伪造空结果或完成状态。最低上下文回归同时核对完整工具schema、精简但保留科学约束的系统指令及送达账本开销，不只检查正文大小。

负责人不再固定裁到18KB，咨询不另设8K输出上限；均服从显式冻结配置。大资料仍需按需查证，不承诺所有系统都能装进任何模型的原生上下文。`update_implementation_state`保存事实和可执行下一步，不记录隐藏思考。

## 定向自然环境与自动扩样

`generate_cases`可一次生成大批手牌条件案例，`cohort`可增加自然拍卖目标。`trial`在campaign中必须声明`sampling`或显式`uniform=true`，不会悄悄把局部机制当均匀试验。

```json
{
  "boards": 256,
  "max_boards": 8192,
  "min_changed_families": 64,
  "sampling": {
    "constraints": {"N": {"hcp": [16, 20]}},
    "dealer": "N",
    "auction": {"reference": "parent", "side": "NS", "prefix": ["Pass", "1S"]}
  }
}
```

参考体系必须是已登记冻结版本。程序从空拍卖自然运行，不注入前缀、不按DDS收益挑牌，也不静默放宽条件。条件过稀或不可达会明确报错，不能伪装成成功样本。

一次工具调用内自动补新牌，直到变化牌族数达到目标或到达`max_boards`／剩余探索额度；无需每批再调用模型。结果记录实际批次、副数、抽取命中、变化覆盖与弃权贡献；覆盖不足明确标注。恢复复用原manifest与已做批次，不重复扣账。保存的诊断案例不是fitness。

## 队列、挑战与融合

- 所有冻结发布保留到候选档案；先成为冠军不占住同代晋升名额。
- 挑战实际开始时冻结届时冠军，使用另一批共同牌比较；记录设计亲本与实际比较亲本。
- 后来更好的候选可以推翻早先胜者；同一候选／实际冠军组合去重，恢复不重复评价。
- 略负的开发结果或未触及改动不再一刀切拦住挑战；无效候选和未完成草稿仍不得参赛。
- 负责人可提名保留候选，也可用`base_candidate`继续非冠军版本。
- `merge_candidates`与执行工具`merge_candidate`进行按语义ID的三方合并；冲突显式报告且不部分修改工作稿。合并必须重新通过真实回归、自然变化见证、冻结与新牌评价。
- `continue_from`可续接本轮未完成任务或引擎修订时保留的草稿；已发布版本必须用`base_candidate`，不能冒充未完成草稿绕过版本检查。

新引擎从`champion_seed_run`续接时同时导入已发布非冠军候选和未完成研究分支，保留案例、测试、笔记和实际工作集。旧成绩只作为历史证据，新run重新评价；旧费用不删除。显式追加授权与仅继承各池真实余额的维护续接分别登记，后者不能重复授予已使用额度。

## 独立维护与错误隔离

`maintenance_budget`单独规定请求、token和时间。接口／schema／JSON错误、截断、传输或模型替换异常及其纠正请求归维护；不消耗有效研究回合。原始响应、未知用量的保守预留、真实计费收据和总账全部保留。正常设计错误、反例、研究讨论仍计研究。

导航schema与真实handler共用定义，避免接口自己接受不了其声明参数。截断响应不执行部分JSON。维护不足时保留草稿，明确显示`blocked_harness`；网关故障隔离到任务，不捏造候选或分数。取消和真正研究预算耗尽仍正常停止，不伪装成维护事件。

### 负责人查证的版本边界

查询当前草稿优先使用`inspect_research_evidence(view="protocol", session="已知会话或保留分支ID")`，不需要填写`candidate`。负责人上下文及`portfolio`返回按真实会话／分支ID生成的`protocol_queries`，可以直接复用其中参数，不必猜会话名或抄写hash。`candidate`单独使用仍只能指向已登记的冻结版本。

草稿的`document_hash`标识已保存的原始IR，`system_hash`标识正规化后的可执行体系；补全默认字段等正规化操作可能使两者不同。工作区摘要明确返回`document_hash`，原有`hash`仍保持文档身份以兼容旧记录；协议查询的`evidence_source`同时返回两种具名身份，原有`hash`仍是可执行身份，不改写历史记录。

如需核对预期版本，可同时传`session`和`candidate`：后者必须是64位小写十六进制hash，并与这份当前草稿的`document_hash`或`system_hash`之一精确相等。因此工作区提供的文档hash不再被误拒，原先使用可执行hash的调用也继续有效。占位字符会在schema校验时被拒绝；其他版本及真正过期的hash不会被忽略或自动换成当前稿，错误明确给出当前两种身份及无需hash的重试方式。没有`session`时仍只接受已登记的冻结版本，不因某个hash曾用于草稿查询就自动登记候选。

未知版本、未知会话或过期hash属于可纠正的查询接口错误：原响应和费用保留，失败请求与纠正请求使用维护池，纠正后继续负责人反馈，不再尝试读取不存在的冻结文件。查询草稿不自动登记、发布、运行测试或DDS，也不把其他hash的旧试验说成当前稿的验证。

已登记冻结文件或已批准工作区真正丢失、被修改、校验失败仍是可信证据故障，明确停止而非吞成接口纠正或伪造成功。此修订改变引擎身份；E015原记录与账单保持不变，续跑需新引擎实验继承保留草稿，不能热改旧hash后直接恢复。

### 维护者负责交付，而不是提交待审建议

campaign维护者使用持久工具会话；`repair_attempts=0`明确关闭维修，非零时由独立维护总资源控制，不再把它当“一次提案”的终止次数。旧episode的追加式补全保持兼容，但不能代表新版维护岗位的能力。

基线未实现分支、非法叫品、公开保证失真均按真实桌号、行动者与冻结体系身份归属；框架／DDS／计分故障单独派工。定向采样中的冻结参考体系错误也保存当时的完整牌与双方定义，不重抽失败牌、不把这次失败占用有效研究回合。**维护分类与弃权分类分离**：非法叫品或不实公开承诺不能因派给维护者就自动计为对手弃权。

维护者的实际循环：

```text
原始牌例／错误归属
  → 空前缀重放，保留失败前进程和精确公告错误
  → 按语义键查询规则、公告、状态与完整传递依赖
  → 编辑隔离工作稿，包括旧规则、参数、优先级和搭档接续
  → 原反例两桌＋保存的256副双向差分回归＋作者边界测试
  → 独立只读复核；退回意见直接成为下一次工程迭代
  → 发布完整新版本，累计同基线已验收修复
  → 新冻结实验重新评测，并继续保留的研究工作
```

无需把整套几千条规则塞进首条消息。`read_incident`、`navigate_system`、`read_system`、`read_result`可补取完整证据；大结果有可分页回读的持久引用，不能用不可补读的17KB摘要代替原定义。`update_implementation_state`保留实际事实和下一步。原`requires_review`工单可以继续处理，不再是无人接手的终态。依赖其他故障时保存工作、派出关联工单，依赖交付后复测。

修复允许必要的旧行为变化，不再以“所有旧规则字节不变”阻止根因修复。程序拒绝修改全局fallback，统计原正常桌是否新增失败及改动见证；独立复核检查体系依据、公告与接续是否一致，不能靠大范围Pass、删除合法承诺或削弱对手帮候选获胜。原反例的全部双方版本组合、随机差分回归都复用配置的`workers`独立进程并行执行，按原牌序汇总相同的完整结果；控制台区分两阶段并显示已完成桌次，而不是让长时间CPU工作看起来卡在模型上。已有修订能否覆盖新工单的预检遇首个失败即交回维护者，不为一个已失败的“全部解决”假设重复跑完整批次。有限差分样本与模型批准不是全空间不降能或最优强度证明。控制台明确显示实际验证分母与局限。

同一重放批次只编译一次不可变工作版本，各CPU工作进程也只加载各个不同的体系版本一次；不能为每桌重新解析整套IR。后续编辑会重新编译，不跨修改复用旧工作定义。

验证完成、失败或中断后立即归还维护者控制，并保存最近一次实际验证结果；不能在模型继续修改时仍将岗位显示为正在运行CPU回归。

### 框架维护也交付代码

campaign框架维护者能读取／编辑隔离的`src`、`tools`和`tests`副本，通过`run_engine_tests`执行实际unittest。交付必须包含已运行的复现回归，并由宿主用**新回归＋原引擎**确认原来确实失败，再验证修订后通过；独立只读复核可继续查完整文件和保存结果。只有诊断或测试计划不能成为已修复状态。

开启`auto_continue_repairs`且有独立维护池时，维修队列持续负责同一框架工单：一个周期返回方案后，直接使用已保存的隔离源码、测试和下一步启动下一周期，直到独立验收或明确阻塞，不因本轮已访问工单而无人接续。`period_supervision`持久记录责任方、调度次数、停滞周期及停止原因；其他工单仍按原优先级轮转。研究池不补贴维修。达到维护余额上限，或连续`max_missed_deliveries`个周期（未配置管理者时为2）没有新增源码、不同测试结果或独立复核证据时明确停止并保留可恢复工单；重复读取及重复跑同稿同项同结果不算进展。repair-only仍有未验收工单时显示阻塞，不标完成。已知旧失败保留，修复必须证明原反例失败、新版通过，不能跳过独立验收。

通过后交付可执行的新引擎副本；续接由该副本单独启动，不改正在运行的源码与历史hash。中断后换引擎续接也保留独立的工程工作稿、原始代码、作者回归、完整结果和退回意见，工具调用去重不会重复应用已完成编辑。此接口当前针对Python框架及其unittest，不承诺自动修复任意外部服务、不可用的求解器依赖或整个主机环境；未完成的工作保留为可恢复维修，不伪装成交付。

### 自动续接与剩余额度

启动时先处理维护积压，并在实现任务之间调度维护，不必等整代结束。验收后`auto_continue_repairs`在campaign默认开启：另建明确记录基线／引擎修订的新实验，继承冠军、已发布候选、未完成草稿、回归及笔记，立即重新评价发布物；按`repair_continuation_mode`继续研究或只评测。旧牌、旧分数、原模型费用留在来源实验，不复制为新成绩。

维修和自动续接只携带研究／维护各自的**剩余**请求、token、时间与比赛配对额度，不偷偷重新授权整包预算。余额不足明确显示续接错误，不借研究池给维护。手工另开全新授权实验与这个“剩余额度续接”是两件不同的事。

旧引擎停机后可在当前引擎导入其完整工单和已完成轮次里的真实故障记录：

```bash
bridge-evolve evolve repair --from-run .runtime/evolution/evo-原运行ID
# 仅修复后重新评测，不启动新研究任务：
bridge-evolve evolve repair --from-run .runtime/evolution/evo-原运行ID --continue-with evaluation
```

控制台“继续维修并自动续接”完成相同操作；不要求用户下载修复JSON后再手工拼配置。当前引擎上的中断维修从原会话恢复，旧引擎则开新维护实验，原运行不改。新控制台能显示阶段、下一步、工具记录、验证分母、关联故障、新版本及后继实验入口；停止的研究不能继续显示“研究继续”。

## 控制台与验证

表单可配置campaign、独立维护／试验额度和大上下文；从旧实验续接不会又写回48回合。详情显示研究／维护账本、真实总费用、机制试验覆盖、挑战实际对手、保留候选／草稿、负责人反馈及原错误；可读下载报告保持同样口径。

专项测试覆盖大批生成、真实DDS定向补样、同代连续替换冠军、三方合并、独立错误账本、工具式维修／复核退回、原失败与修订后的真实工程测试、修订引擎独立进程中的实际DDS重评测，以及多次续接的草稿与剩余额度迁移。它们证明框架行为，不证明真实模型已提高体系强度或单位token产出；必须用实际新研究结果检验。

## 研究保交付与工程解除阻塞

启用`campaign_manager`后，交付目标独立保存在`management.deliveries`，记录研究团队负责人、原假设、当前工作区、接手历史、下一验收点、真实证据及工程依赖。暂停或结束执行者不会撤销目标，草稿里程碑也不等于目标完成。管理者用`delivery_outcome`提交当前版回归／真实试验／门禁候选，或带真实反例的否定结论；宿主拒绝用草稿、暂停、工具参数错误或工程故障冒充研究验收。正式成绩和晋升规则不变。

没有可运行主线时，优先把同一目标和当前草稿交给接手任务，要求复用已读证据、改方法，先补最小可检验产物。原始IR分页读取即使在编译失败时也会进入工作集；继承时核对当前内容，失效页面不冒充现行定义。接手次数不会因改任务名清零；连续换手仍无验收结果则明确`blocked_delivery`，目标与责任仍保留，不继续开无关假说、不报告成功。新任务可用`delivery_id`关联同一目标，用`requires=["compiled"]`或`["tests"]`声明前置证据；不满足时等待，而不是先运行必定失败的后续验证。

真实基线故障与开发试验中的框架故障关联原研究目标；工程队优先处理阻塞目标的工单及其依赖。通过参数校验后，查询工具意外抛出的Python异常也保存精确输入和现场，交现有隔离工程岗位复现／修改／回归；一般接口事故同一会话重复出现才强制等待，文件／运行资产缺失等`OSError`首次即阻塞派单。框架故障明确标记`framework`并记维护账，不要求研究者反复修改正确参数。不存在的IR节点／数组位置是显式输入错误；咨询中的`/tests`和`/workspace/...`读取真实工作区，缺失节点在`pointer_errors`中逐项说明，不伪造空结果。普通参数错误、候选IR设计错误不转工程工单。已有的原版反例失败、修订版通过及独立复核仍是工程验收门禁。

`accepted_for_next_run`／`accepted_engine_revision`只表示修订已交付，不能解除旧冻结引擎上的研究阻塞；必须在修订真正生效、工单成为`resolved_by_revision`后，从保存工作区接续，不重置账本或旧成绩。阻塞期间的纯等待不计作研究者未交付。

每次新研究请求前检查能否同时承担该请求及一次精简交付审查，保留请求、token和时间空间；不足时提前交还，不能借维护额度扩写协议。初次启动已经不够一个完整周期时，宿主直接保留责任并说明资源阻塞，不付费询问一个已知答案。预算、取消、异常及正常退出都会无模型调用地保存当前版本和实际验收快照，清理仍在运行／已领取的状态；存在未验收目标时，全局不标`completed`。控制台展示责任、下一步、工程依赖、接手及停机快照；这些运营指标均不进入fitness。

### 工程定位、完整部署与故障恢复

工程执行者和独立审查者均可使用`list_engine_files(glob, offset, limit)`与`search_engine_files(query, glob, offset, limit)`：基于实际隔离文件返回可分页路径、字面文本命中及行号，不再猜测源码路径。初始上下文只给入口索引，正文按需读取；文档只读，编辑仍限原有源码／测试边界，路径穿越及逃逸符号链接被拒绝。

隔离副本记录已验收基底与修复覆盖链，不允许旧分支覆盖新修复。如果等待期间基底变更，创建基于最新修订的新分支，保留旧源码与测试，将旧修改作为可分页读取的`prior_branch`提案交给维护者移植，旧测试不冒充新基底上的通过证据。已解决故障在新引擎重现时建立独立维修工作区，同时沿用稳定事故指纹计算恢复上限，不因改引擎目录或工单号清零。

`evolution.runtime.freeze_engine`统一打包源码、动态工具、全部批准参考文档／示例和控制台浏览器资源，生成`runtime-manifest.json`。引擎身份同时覆盖运行资产内容；冻结前、冻结后及跨引擎交接均验证完整性。不得给旧冻结目录补文件后冒称仍是原引擎，也不把旧身份算法产生的验收hash直接改写为新hash。

主控制器的文件／执行异常同样记录阻塞工单和有界源码定位信息。隔离修订通过原反例失败、新版本通过及独立审查后，在安全检查点收口并交给新引擎，不热改旧进程；有活动交付周期时先要求返回当前最佳方案。`failed`仅在有匹配故障的已验收修订时允许自动续接，未知失败不会盲目重启。同一事故最多跨三个新引擎自动恢复；余额只继承真实剩余，历史失败／评分不改写。

新实验核对预期引擎身份，保存`recovery`与历史；只有实际研究工具成功，才写`recovery-receipt.json`并显示`research_resumed`，进程启动本身不算恢复。子进程启动／身份验证失败明确记为阻塞及`continuation_error`，不伪报已恢复。

### 临时方案必须可以真正进入草稿

研究用`return_solution`除四项必填说明外，可附`provisional_patch`：当前完整`document_hash`、原子`edits`及明确的`falsification`。宿主立即尝试写入真实体系草稿，允许设计不成熟或尚未编译／回归通过；不从自由文本中猜补丁。工程岗位不得用此字段部署引擎。

应用与来源账本一起原子保存，包含涉及路径、前后hash、具体方案、依据、局限及证伪条件，明确`applied_provisional`、写入时未验证、未验收。有临时提案的工作区在替换文件前持久化前后字节hash；文件已落盘而总账未更新的崩溃可核对后恢复，写入未发生则保留旧稿等待重放，匹配不到任何一侧的文件必须拒绝恢复。控制台摘要只在实际写入后更新。账本随阶段快照、冻结工作区和后继研究继承，控制台分别显示“方案已返回”“临时补丁已写入”“当前验证”“发布／晋升”。只在日志写建议、不改草稿，不算临时应用。

过期基准或非法补丁明确记录`not_applied`与错误，原稿不发生部分修改；具体方案仍可按期返回，不因应用失败丢失交付。崩溃重放同一交付不会重复应用补丁。临时应用不生成通过测试、发布候选或晋升记录，原科学门禁保持不变。
