## 当前重点：先完成可分析的研究结果

2026-11-05起按[Auto-Research计划](14-autoresearch-plan.md)先修上下文/参考缺口，再交付评价解耦和无模型评价，用5–10个不同候选验证流程。失败或无提升保留为结论，不强求晋级；重复发布同一哈希不增加样本数。

之后的1NT方法Pilot比较固定传统模块、Local Editing、Global Protocol Design；Blank初始化留作后续消融。B/C共享起点、入口、外围、模型、预定资源口径及统一评测器，并做多个独立研究重复。报告条件与总体IMP、有效性/覆盖分母、结构变化、实际成本和完成率，不奖励新颖性。

这套方法对照及模块合同尚未接线；不能因为局部1NT可以单独运行，就说已支持该实验。evaluation-only也是待实现能力，不把建议名称写成已有命令。

下面E001–E006配置与结果为历史/原型入口，某些配置依赖本地历史牌例或运行ID，克隆仓库不携带这些数据。代码与独立回归所需的小型夹具另行版本化；新比较仍现场随机发牌。

## E002：旧版局部Agent提案实验

目标是在全新10000个基础牌族上分别显著优于当前CCBA/精确工程v5.5.3；两者同时作为固定锚点和起始谱系。工作流程为评测、统计/问题聚类、Agent提案、候选校验、共同牌筛选、新牌确认晋级，再进入下一代。

[E002实现与完整协议](12-self-evolution.md)列出了基线完整哈希、数据规模、Agent权限、建议效果门槛、双比较及重复尝试处理、停止预算和实施边界。**不预留数据集**：每个新阶段现场随机生成，同轮共同牌，恢复复用原轮次；选定候选后才现场生成10000副。

需要额外保存：问题组及其处理覆盖、分析包/证据引用、父子IR补丁和说明、共同牌的逐牌差值、确认尝试/错误预算、谱系冠军指针和模型/计算成本。完整轨迹使用[紧凑记录](11-compact-records.md)，Agent按需展开。

首版`evolve init/run/resume/status/cancel/verify`已实现，[pilot配置](../experiments/e002-pilot.json)可直接运行，首页也可开启任务。先用`--profile smoke`跑三代工程验证，再扩大；smoke/pilot默认不自动运行10000副。以下E001保留为局部实验与诊断选项，不再是进入进化的唯一前置路径。

## 1. 首个实验 E001

问题：固定 15–17 HCP 均型 1NT 开叫、对手始终 Pass 时，自动修改应叫/再叫，能否比冻结基准获得更高的同牌平均 IMP？

模式为 `uncontested-1nt`。N 满足开叫条件，固定前缀 N 1NT、E Pass，S 行动。初始体系必须补齐这一路径的全部后续与兜底；其他分支无需据此宣称完整体系。

数据默认从均匀随机发牌后按固定开叫条件筛选。记录接受率、生成算法和种子。初版局况按预先固定的权重抽样，若生成同牌多局况变体，保持同 split 并按牌族统计。

建议先用数十副真实求解牌验证整个流程，再用约一千副做工程运行；正式比较按预先确定的样本量扩大。数量只是工程默认值，不代表已有统计功效保证。

第一批变异可以只探索无将邀请和接受邀请的点力/牌型边界。随后引入高花发现、转移和套质量等结构；每次协议变化同时更新所有相关角色。不要把这个局部题目永久当作项目能力上限。

## 2. 运行配置契约

编码时提供一个经 schema 校验的配置文件，最少包含：

```yaml
experiment_id: E001
mode: uncontested-1nt
oracle_kind: dds
dataset_manifest: <不可变 manifest 路径>
split: validation
candidate_systems: <内容哈希列表>
reference_system: <固定基准内容哈希>
incumbent_system: <当前冠军内容哈希>
fixed_prefix: <显式座位与叫品序列>
sampling_profile: <开叫条件和局况权重>
seed: <调度及统计重采样种子>
sample_size: <基础牌族数量>
confidence_method: paired-family-bootstrap
output_directory: <新的运行目录>
```

竞争实验另加冻结的对手列表、权重、两桌布局和公开协议版本。固定基准用于跨代锚定；incumbent 用于本轮晋级，二者可以相同但不能混淆。

上面是单次评测配置示意，不是进化CLI配置。E002实际配置使用`profile/baselines/source/modules/boards/generations`及资源/统计预算，不接收外部`test`数据文件；评测端在各阶段按需抽样，`evolve verify --run ...`可单独发起候选冻结后的新10000副检测。

## 3. 每个运行保存什么

```text
run.json                 # 版本、哈希、配置、种子、状态、起止时间
systems/<hash>.json      # 实际执行的体系，不是会被覆盖的路径引用
systems/<hash>.md        # 对应完整说明
mutations.jsonl          # 父版本、提案、patch、校验结果
boards.jsonl             # 逐牌 ID、分数、IMP、定约和错误引用
auctions.jsonl           # 完整公开历史与评测端私有 decision trace
summary.json             # 机器可读统计
report.md                # 面向人的解释
```

上面是单次研究结果的逻辑内容。E002实际目录为`config.json`、`state.json`、冻结`systems/`、`analysis/`、`proposals/`、逐轮`rounds/`、压缩`cache.sqlite`及`report.md`。运行目录不能暴露给运行期策略；提案端只接收批准的历史分析包。完成的检测结果可供后续分析，下一次提升结论另抽新牌并沿用预定重复检验预算。

## 4. 叫品与分支统计

按完整上下文或规则 ID 聚合，不能把所有“2D”混在一起。至少记录：

- 分支到达次数和占基础牌例比例。
- 该分支后的最终定约、庄位和成败分布。
- 同牌修改前后收益、正负贡献最大的牌例、样本量。
- 规则覆盖、重叠/失败次数与兜底触发次数。

“平均最终分高”不能直接说明该叫品好，因为强牌更容易进入某些分支。低频也不等于浪费。

`触发概率 × 触发时可实现的增益` 只用于给研究假设排序，不是精确适应度，也不是要求增加叫品使用频率。结构修改可能改变进入分支的分布，最终必须用完整策略在共同牌例上重测。

## 5. 反事实分析

初版通过候选整体协议与父体系在同一批完整牌例上的重放进行比较。不要逐副事后选择最佳动作，再把这些互相不一致的选择拼成策略成绩。

以后加入局部 rollout 时，需要固定行动者可见信息，对未知手牌按历史和当前协议形成的分布采样，并明确行动后的搭档/对手继续策略。仅满足硬性牌型条件的均匀采样不一定等于正确后验，应标注近似。

允许在诊断时看完整牌，但“这副牌应该怎么叫”只能作为假设来源，不能替代总体期望收益验证。

## 6. 结果报告模板

每次实验至少回答：

1. 修改了什么可执行语义，涉及哪些角色和协议？
2. 为什么预计它有收益？可证伪的预测是什么？
3. 使用什么模式、样本、局况、对手和 DDS 版本？
4. 相对固定基准以及 incumbent 的平均 IMP、配对差值区间是多少？
5. 哪类牌贡献最大，损失在哪里，是否依赖少量异常牌？
6. 当前结论属于流程演示、探索性信号、独立确认还是最终保留测试？
7. 有哪些冻结分支、样本偏差、DD 近似或对手适应限制？

同样有效的结果包括“本轮没有证据支持改进”。不能为了展示自动进化而强行替换冠军。

## 7. 研究结论的措辞

可写：“在 E001 的固定开叫分布、对手 Pass 和 DDS 计分下，候选相对基准的配对收益为……”。

不可写：“发现了桥牌最优体系”“已经达到实战上限”，或把局部实验的收益外推为所有竞争叫牌的优势。
