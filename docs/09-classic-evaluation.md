# 经典体系工程移植、真实 DDS 与同牌评测

> 2026-11-05：当前冻结工程参考为v5.5.4，仍有E006复现的未实现出口和不成立的红桃下界，不能作无条件可信基线。近期先按[参考修订验收](14-autoresearch-plan.md#3-r0--p0先修结果边界与固定参考)修复、版本化，再正式比较。后文按日期保留历史交付，原`results/`/`datasets/`/`.runtime/`证据只在本地，不随Git发布。

## 1. 先明确比较对象

本次版本是以用户提供的CCBA 2.2、精确1.1.1为来源的**可执行工程基线**，不是两份手册全部约定的逐条完整复现。

- [CCBA v5.5.4 IR](../systems/classics-v5.5.4-compact/ccba.json)；
- [精确 v5.5.4 IR](../systems/classics-v5.5.4-compact/prec.json)；
- [迁移清单](../systems/classics-v5.5.4-compact/migration.json)：源文档SHA-256、版本、正文优先规则、明确的评估公式、已移植模块和被压缩/未逐条移植的部分。对应中文规范用`system render <IR>`同源生成，生成文件不重复纳入Git。

保留了不同开叫结构、不同无将范围与应叫、强梅花、二盖一/反加叫/Jacoby/Bergen/Drury、转移/斯台曼/傀儡、弱二问叫、Gerber、关键张及自然竞争等主要结构。但双路重询/XYZ/第四花色、部分细分牌型接力、Lebensohl/Michaels竞争细项、排除问叫/问Q/侧K/大满贯搜索尚未逐条完整迁移，而按明示自然续叫策略完成。

这限制了研究结论：**只能比较这两个具体内容哈希的工程版本，不能把数字当成原版CCBA与精确在人类实战中的实力差距。** 规则数量、说明篇幅或复杂度不进入成绩。

所有运行期叫牌仍由导出的v2 IR执行；[编译器](../src/bridge_evolve/systems/classics.py)只生成IR，不在决策时调用，也没有藏一个Python叫牌模型。

重新生成并核对原始文档：

```bash
.venv/bin/bridge-evolve system build-classics --output systems/classics --sources ..
```

`--sources`要求目录中两份原始docx的哈希与迁移来源一致，否则拒绝生成。正文与摘要冲突取正文；“好套/止张/赢墩”等采用清单中的精确公式，而不是运行时问LLM。

## 2. 真实DDS

采用官方DDS **2.9.0**，源码commit：

```text
8d75755c8df81999557758c9757514edb94017bc
```

许可证为Apache-2.0。使用旧C接口`CalcDDtablePBN`，通过标准库ctypes调用，不需要Python dds3包。每个Deal实际求解20项墩数。

```bash
# 新机器需要可用的C++编译器与下载公开源码的网络。
.venv/bin/python tools/dds/build.py
.venv/bin/bridge-evolve doctor --json --require-dds

# 强制真实求解验收；缺少库时失败，不把skip当接入成功。
BRIDGE_DDS_REQUIRED=1 PYTHONPATH=tests \
  .venv/bin/python -X faulthandler -m unittest test_oracle test_diagnostics -q
```

已核对五组独立的官方公开牌例表、座位旋转、重复求解与线程调用。该真实验收共28项，实际全部通过，零跳过。原生数组到Python的轴显式转换：

- 行：N、E、S、W；
- 列：C、D、H、S、NT；
- 值：该实际庄位的可得墩数，0–13。

原生调用单线程，并由进程级锁串行化。构建记录编译器、标志、库SHA-256及补丁标识；Linux可用内存探测补丁只调整资源估计，并禁用不安全的ELF自动初始化钩子，不修改求解算法。实际版本/构建状态以doctor和运行清单为准。

库默认在`.runtime/dds/libdds.so`。从独立安装的wheel调用时可指定：

```bash
export BRIDGE_DDS_LIBRARY=/absolute/project/path/.runtime/dds/libdds.so
```

旁边必须有匹配的`libdds.build.json`，适配器在加载前检查固定来源和库哈希。不要只复制一个来源不明的同名动态库。

## 3. 数据和缓存

每“副”是52张牌均匀分给四人，不是只有一个人的13张牌。不按开叫点力/牌型筛选，任意位置都可以开叫或竞叫。

```bash
.venv/bin/bridge-evolve dataset generate \
  --output datasets/new-heldout --count 1000 --seed 26720261024 --split test

.venv/bin/bridge-evolve oracle precompute \
  --dataset datasets/new-heldout/manifest.json --cache .runtime/dds/tables.sqlite
```

生成算法和Python版本写进manifest。发牌人/局况按固定16副周期平衡调度；完整牌例按内容校验，座位循环旋转归同一基础牌族。文件内容、条数、重复牌族和52张牌都检查；内容损坏不是丢掉那副继续跑。

SQLite墩数缓存以精确N/E/S/W手牌内容和完整真实DDS来源为键，不含发牌人或局况。源数据相同而版本/构建不同不会混用。原生失败不写入成功缓存；fixture/mock来源不能进入正式缓存。

数据集ID、索引、种子、DDS表和另一桌结果不进入Observation。DDS只在叫牌完成后由评测端查询。

## 4. 两桌同牌成绩

对每一基础Board：

```text
桌1：A=CCBA坐NS，B=精确坐EW，得到S1_NS。
桌2：B=精确坐NS，A=CCBA坐EW，得到S2_NS。

本副A分差 = S1_NS - S2_NS
本副A IMP = signed_imp(S1_NS - S2_NS)
```

两桌手牌、发牌人、局况完全相同，只交换体系位置。用实际庄位和定约花色查DDS，再按阶数、局况、X/XX计分，统一NS视角。全Pass得0，无庄家。

先逐副换IMP，再求平均。1000副产生2000桌，但**只有1000个独立基础样本**。95%区间按基础牌族配对bootstrap，样本量、重采样次数与种子在运行前固定。没有中途看区间提前停。

真实开发验收包括八副自比逐副严格0，以及交换A/B后两桌结果对应、IMP逐副严格反号。

## 6. 失败与保留数据的处理

第一批1000副的尝试在索引608遇到赌博3NT后的4C修正协议缺陷，立即停止，保留 [失败清单](../results/ccba-prec-1000-v1/run.json)，**没有发布部分成绩，也没有删除/替换失败牌**。

检查该牌后，为赌博3NT的Pass-or-correct增加独立的4C/4D路径和回归测试。原保留集已写入 [consumed.json](../datasets/ccba-prec-test-1000/consumed.json)，不能再用作独立最终测试。评测器会拒绝把这类已消耗test继续当成新test运行。

最终改用全新种子生成的1000副，并重做1000份真实DDS表；旧失败结果不拼接、不计零分、不伪装成功。迁移清单记录这一版本历史。

程序失败保留active_board、错误类型/消息和已完成数量，状态为failed；只有全部牌例完成后才写成功汇总及最终报告。基础设施错误和候选协议错误不会变成普通分数。

新增实际协议包括双路重询/精确XYZ、第四花色逼局、逆叫弱牌出口、加叫后2NT询问、Mini-Splinter/Splinter、Bergen/Jacoby分档、帮张与逆朱瑞、精确4333/44接力及2C/2D问叫、Smolen/低花斯台曼、Michaels/特殊2NT/Landy/马歇、莱本索尔/无将逃叫、否定性加倍，以及RKCB后问Q/问K和缺门关键张。

### 暂定评估

- 无明示边界时：邀请参考合计23HCP；高花/无将成局25、低花29。双路重询按搭档公开下界划分邀请/逼局；普通邀请可用公开区间中值。
- 好套：至少5张且AKQ至少两张；坚固套至少6张且含AKQ。止张：A、Kx、Qxx或JTxx及以上。
- Jacoby高限16+，中限14-15或4控制；A计2控制、K计1控制。帮张接受与Mini-Splinter单缺回答的顺序均写入清单。
- 缺门关键张正文遗漏1.5档且与附录冲突，暂采用附录的0-0.5/1/1.5/2/2.5五档，3+直接大满贯；缺门A不计，将牌Q计半张。
- 0/3、1/4关键张采用保守下界，不根据搭档私牌选择高档。其余具体边界以冻结IR为准。

协议映射不等于逐条形式等价证明；罕见多轮干扰、部分扣叫和终局选择仍由明示自然规则补全。首攻、打牌信号和裁判程序不属于本轮叫牌执行范围。该版本是带明确推断的可执行翻译，不是原版人类搭档的唯一实现。

npm --prefix tools/board-viewer ci --ignore-scripts

### 远程端口转发与可信来源

服务器仍只监听`127.0.0.1:8765`。在VS Code“端口”面板转发远端8765，然后打开面板给出的本地地址；本地8765被占用时可能映射为8766等，必须以实际本地地址为准。无需开放服务器防火墙或改成监听`0.0.0.0`。

也可以在**自己的电脑终端**运行SSH转发（替换`user@server`）：

```bash
ssh -N -L 18765:127.0.0.1:8765 user@server
```

随后本地浏览器打开 `http://localhost:18765`。本地18765和服务器8765不必相同；默认校验允许localhost、127.0.0.1和IPv6本机地址上的有效端口，但Origin仍需与浏览器访问地址一致。未配置的跨端口来源、外站来源和伪造Host仍拒绝，不能通过`X-Forwarded-Host`等请求头自动扩大信任。

若反向代理改写Host或在HTTPS处终止，服务器收到的Host可能不同于浏览器Origin。此时在**服务器项目目录**启动时明确配置浏览器实际来源，例如：

```bash
.venv/bin/python tools/board_viewer.py --port 8765 \
  --allow-origin http://localhost:18765 \
  --allow-origin http://127.0.0.1:18765
```

HTTPS代理可使用精确的`--allow-origin https://你的可信代理域名`。该参数可重复，只接受协议、域名和可选端口；拒绝通配符、凭据、路径、查询和片段。即使配置可信来源，服务仍只绑定服务器回环地址；公共代理必须由用户的SSH/VS Code隧道或认证反向代理保护，因为审查数据包含完整手牌和私有trace。

`访问来源未获允许`（旧消息为`Only same-origin local requests are accepted.`）表示请求地址或来源未在上述规则中获准，不是牌例格式错误。优先核对浏览器实际地址和本地映射端口，再按需配置精确来源，不要直接关闭校验。

## 12. v4点力上下界与自然3NT修正

v3只把HCP下界接入共享账本，零散`open_max/res_max`没有完整收紧和审计。v4增加双方及联手的公开HCP区间、本人私有联手区间和开叫前Pass的座位上界。旧版IR/结果不覆盖。

### 区间与Pass

- 精确1D为11-15；CCBA1C为12-21。当前实际开叫规则仍允许11点高花、第三家9点轻开，因此不能把CCBA全部开叫统一称为12+。
- 公开下界取max、公开上界取min；每个座位的上界与其captain/responder角色范围相交，角色未确定时也不会遗失之前的Pass信息。空区间明确报错。
- 精确的未开叫Pass最多10HCP，CCBA最多11HCP：这是根据当前全部开叫分支的覆盖得到的保证。竞争Pass、埋伏Pass及开叫后的Pass不自动当作弱牌，也不跨牌保存。
- 本人13HCP加搭档公开11-15，私有联手区间为24-28；它与公共联手区间再相交。双方都能重建公开范围，私有估计只留在本人策略/trace。
- 上界未有保证时保持40；不把“可能有这么多点”当作已经有这么多点。显示器显示区间、双方范围和Pass座位限制；旧记录无上界时不事后猜填。

### 3NT的直接根因

已消耗v3日志中有9次普通自然3NT来自`competition.natural_nt_3`，只检查应叫人13点，甚至联手下界21也会进局。这不是单纯缺上界：决策门槛本身也错误。v4普通自然3NT要求联手下界25，竞争2NT邀请要求下界23；精确2C无配合与莱本索尔自然3NT也检查联手下界。

对旧第260副进行同手牌、同前缀的交互复核：原序列为`P P 1D P P 1H P 3NT`；v4在相同决策改为1NT，私有区间21-24。这是该次动作的修正，不把后续双方重新竞争的最终定约冒称为1NT，也不将单副修正当作整体成绩证明。

人工问答中的3NT、赌博性长套3NT以及体系明示的逼局/逆叫进局路径须单独解释，不能只按叫品字面全部禁掉。本次新1000副中，检查修复的普通自然3NT分支7次，均满足25点下界；其余低于25的3NT按上述上下文分类，不声称每个3NT都保证25HCP。

新增上界审计还修正了旧声明/协议冲突：

- 精确Jacoby高限三阶将牌按原文为14-15点且6+张，不是16+；缺少35点保证时不自动邀请大满贯。
- 邀请加叫上界按开叫范围与“24减搭档已知下界”取交集，不把实际18点错误排除在固定16-17之外。
- 精确弱无将2NT保留为低花转移；无高花10-11点邀请明确走2C非逼叫Stayman后2NT，不再用自然邀请冒充转移。

- 自然争叫、技术加倍、强梅花部分正应叫等没有保证的旧上限移除，不把启发式标签直接当硬性上界。

## 13. 自然叫品语义完整性审查（2026-10-27）

用户要求检查第580副之外的类似遗漏。本轮保持v4运行期源码、IR和原成绩不变，仅增加只读`semantics`审查；[完整中文报告](../results/ccba-prec-translation-v4-1000/semantic-review/audit.md)和[机器证据](../results/ccba-prec-translation-v4-1000/semantic-review/audit.json)状态为`completed-with-findings`，不是策略验收通过。

### 范围和结果

静态阅读全部15个行为编译模块，按公共前缀执行112次定向契约检查：75次问题实例、37次正确对照、0未复现。相同模板在CCBA/精确中的实例分别计数，不等于75个独立bug；这些是为检查语义而选取的场景，不能当作随机总体错误率。场景检验待行动牌手真实选择的叫品，不只检查字段存在；但不证明每个输入前缀都能由当前两方策略完整到达。

### 高优先级发现

当前角色的点力/长度范围可能包含此前已经知道的信息，摘要称为“当前公开可保证”；只有新增区才表示本次进一步披露。数字是HCP或张数，不把调整点、实际手牌或某个私有发送分支的较强条件混进去。

## 20. 支持问叫、满贯控制续叫与DDS/par（2026-10-29）

### 第772副与支持质量

这里的“旧第772副”指v5.3的`index=771`，不是新种子数据的同号手牌。原精确桌`W 1C–E 1NT–W 2H–E 3S`中，2H支持问叫没有记录问叫套；3S六级答档虽然记了16+点、红桃为将牌，却没有记录支持长度，因此W缺少公开配合，最终停E3NT，DDS13墩。另一桌原已叫到W6H、13墩。

精确原文P295–298规定支持为Qxx/xxxx以上，六级区分8–10、11–13、16+点与有无支持。v5.4.2同步发送、公开解释和后续：

- 当前支持问叫发送规则要求被问套至少五张，因此公开记录5+；没有把个别负应叫后的四张例外泛化到本路径。
- 有支持档保证至少三张且含Q或更高大牌，或至少四张；分别记录张数下界及`*_support_quality`并集保证。不能把它简化成“一定有Q”或“一定四张”。
- 无支持档记录`*_support_denied`及至多三张。非否定档的`False`只是未知，不表示没有支持/控制。
- 1C后的平衡1NT/2S答叫保留当前发送分支共同保证的四套2–4张；人工答叫3S不误添五张黑桃。
- 若本人握该套AKQ，才可在**本人私有推断**中排除搭档“三张带大牌”分支，推得搭档至少四张；不写回公开账本。旧772的公开红桃下界为8张，W的私有下界为9张。

新候选在同一旧牌上经4C控制、4NT关键张、5S“两关键张且有将牌Q”到达6H。这里没有依据DDS把结果反向拼进策略；DDS只在两桌叫完后评价。

### 满贯邀请与控制续叫

新增`slam_cue`公开阶段，控制与邀请来自同一可执行IR，而不是事后解释私有命中：

- 在公开确认八张配合且逼局的路径中，回到低于成局的原将牌是邀请满贯并要求控制续叫；低于该将牌成局位置的新花作为首轮/次轮控制。记录`*_control`保证A、K或单缺的并集，不把扣叫解释为自然四/五张套。
- 当前工程策略以本人手牌加公开下界30 HCP，或28 HCP且九张将牌、短套、至少5控制值（A=2/K=1）为主动试探门槛。已经作出邀请后，搭档可扣叫合作或回成局；没有把“试探”升级为强迫六阶。
- 精确正应叫后明确的七张以上AKQ独立套跳再叫要求开始扣叫。此处“独立可打”的实现是明确、保守的工程判定，不宣称覆盖原文全部独立套情形。
- 确认边花控制后才进入关键张；保留有歧义的0/3、1/4下界，不读取搭档真实牌来挑高档。高花问叫至少两关键张；方片至少三；草花至少四且本人有将牌Q，避免问叫答档越过安全退路后盲目冲六阶。
- 现有Q/K、排除关键张路径保留；有缺门的排除问叫不被新的通用4NT抢走。没有已定将牌的自然NT路径保留31点邀贯、33/37点接受小/大满贯的量化后续。
- 已公开标记为人工的Splinter/控制叫不凭字面3NT/4H等清除逼局。旧冻结IR不被补入新标签，原叫牌及原审计结论不改写。

## 21. v5.5.2：把可能性试探与最终承诺分开（2026-10-29）

### 实际确认的邀局缺口

不是所有旧邀局都要求先有24/25点下界：标准15–17无将后的8–9点定量邀请、简单双高加叫中的部分中值/帮张分支原来已经存在。但通用续叫有两个可复现缺口：

- 自然2NT邀请只接在最近1NT之后，导致`1S–1NT–2S`后的合适均型牌不能用2NT探询。
- 简单加叫后的部分三阶原高花邀请没有设置`invite_game`，也没有公开本次额外牌力的共同下界；接收方继续按最初11点开叫下界处理，可能在实际够进局时Pass。

新逻辑使用可达25点的上界，再结合本人额外价值和有限区间中值；无上界不被当作均匀分布取中值。邀请的公开点力只取所有发送分支的共同保证，接收方仍须结合自己的真实牌力接受或拒绝，不能因为“可能25”就自动进局。15–17无将的8点邀请等原有结构保留，16–19等范围根据上端计算可发送的共同下界。

[完整牌例回归](../results/classics-v5.5.2-potential-validation/game-invitation-regression.json)使用相同合法52张牌、固定全Pass对手及真实DDS：开叫人17点、应叫人10点，旧版`1S–2S–3S`后Pass，最终3S，DDS12墩、NS230；新版公开邀请者至少15点，接收方10点足以接受到4S，仍12墩、NS480。这个定向全Pass反例不计入1000副样本，也不冒称体系强度比较。

### 有将满贯的试探入口

当前牌手只使用自己的手牌和公开协议，分别计算联手HCP可能区间、将牌长度、本人控制值、短套及搭档短套位置的浪费点。

- 可能上界达到32点即可进入考虑；若有明确牌型价值，可能上界29点也允许探索。不存在“先有30点下界才准邀请”的统一条件。
- 本人控制值至少3（A=2/K=1），且比自己的公开下界多至少2点；或者有九张配合与边花单缺、六张好将牌、搭档短套处无K/Q/J浪费且控制较好等实际价值。未知40上界本身不够触发。
- 二盖一逼局后，在本人实际长度加搭档公开保证可确认八张配合时，允许低位回原花色定将并保留探索空间；即使本人就在公开低限，也不必先直接叫成局。该叫品不虚报额外HCP，下一个牌手可展示控制或回局。
- Splinter支持长度明确为四张，已知短套同步记作控制；先前保守地只写三张会损失配合价值。控制扣叫仍表示A/K/单缺并集，不冒称自然长套。
- 覆盖自然、开叫人再叫、应叫人再叫、转移/斯台曼后续、部分强支持及短套选择阶段，不抢走必须完成的专用接力答叫。
- 账本暂记某高花、但实际只能保证七张配合时，允许先在低位明确另一门八张配合并重定将牌；不能暗中自然叫5C/5D，却让搭档按旧高花的排除关键张理解。控制叫前也先把当前八张配合公开确认，避免同一低花叫品同时被发送为自然支持和解读为控制。

## 22. v5.5.3：第55副的定量邀贯与Gerber止叫（2026-11-02）

### 实际原因

这里指v5.5.2的1000副批次`index=54`，南发牌、双方有局：

- 南：`A8.AK64.QJ865.J6`，15 HCP，精确弱1NT开叫。
- 北：`KQ.Q75.AK9.KQ543`，19 HCP，均型，看到的联手区间32–34 HCP。

精确桌的冻结历史实际是`S1NT–N4C–S4S–N4NT`（省略敌方Pass）。北家没有草花A，旧优先级先选Gerber；南家4S显示两个A。北家按自己的19加开叫下界13得到32，尚未满足Gerber后直接选择小满贯的33点门槛，于是走`gerber.retreat`到4NT并转入`finished`。此时南家虽然能按自己的15和搭档公开18+保证33点，却只会收到止叫阶段，命中`finished.stop_completed`。所以缺陷在**入口误选及邀请机会丢失**，不是直接定量4NT的接受门槛算错。

不能把所有Gerber后的4NT改成新邀请：相同叫品还承载缺A或牌力不足时的真实退路，贸然重解释会让原本应止叫的牌越级。

### 修正及可见信息

普通NT应叫的Gerber入口新增`total_min >= 33`，只在已达到小满贯点力下界、还需核查A时使用。均型的可能区间包含33、但下界还不足33时，仍遵循v5.5.2的可能性/非低限条件，走现有4NT定量邀贯；既有高花探查、私有信息边界、低限退出及满贯接受门槛不变。

第55副新路径为`S1NT–N4NT–S6NT`。4NT只公开北家**18+ HCP**的共同下界，而不是偷读真实19点。南家用自己的15加18得到已知33，选择6NT；同一邀请下，13/14点开叫仍可拒绝，不能凭上界自动进贯。Gerber后的4NT仍是止叫，显示器现在明确区分“定量邀贯（非问A/关键张）”与“Gerber问A后的无将止叫”。

独立新版本：[CCBA IR](../systems/classics-v5.5.3-compact/ccba.json)、[精确IR](../systems/classics-v5.5.3-compact/prec.json)及同目录完整同源说明。[共享表达式展开核对](../results/classics-v5.5.3-nt55-validation/surgical-scope.json)确认，两体系除名称和上述一个Gerber入口条件外，其他决策规则、优先级、特征、公开转移与声明逐项相同。
